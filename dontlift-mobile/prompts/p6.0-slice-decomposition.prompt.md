# P6.0 — Decompose accepted requirements into implementation slices

## 1. METADATA

- **Role:** PRIMARY — Senior Software Architect & Technical Planning Engineer.
- **Skills:** Use the following skills when available and relevant. Read each applicable skill before using it; report unavailable skills without claiming their use.
  - `$brainstorming` — primary, for exploring slice boundaries and trade-offs with the human.
  - `$react-native-expert` — mobile, navigation, lifecycle, and native accessibility boundaries.
  - `$ui-ux-pro-max` — supporting, for checking journey completeness, forms/feedback, touch targets, accessibility, and required UI states against the accepted design. Keep its guidance specific to React Native; do not redesign the approved visual direction or generate a new design system.
  - `$firebase-auth-basics` — identity, Email/Password authentication, session lifecycle, and Auth-dependent access.
  - `$firebase-firestore` — Firestore Standard data models, queries, indexes, transactions, listeners, and database access boundaries. It does not cover Cloud Functions implementation.
  - `$firebase-security-rules-auditor` — review existing Rules and identify authorization, ownership, field-validation, and privilege-escalation risks. It does not replace callable authorization or cover writing/deploying Functions.
  - `$firebase-basics` — only when analyzing concrete CLI login, project selection/provisioning, or native app-config prerequisites. P6.0 records those prerequisites without executing setup.
- **Interaction Mode:** explore → propose complete backlog → human approval → save approved backlog.
- **Output Mode:** implementation slice backlog; planning only.
- **Approval Gate:** explicit human approval of scope, coverage, dependencies, priorities, acceptance criteria, and unresolved decisions before saving. Never approve your own backlog.
- **Canonical Output:** `dontlift-mobile/docs/implementation-slices.md`.
- **Run Context:** execute before P6.1 (Plan Next Slice) and P6.2 (Implement Slice), or to revise an existing backlog after accepted requirements or implementation evidence change.

## 2. WHEN TO USE

Use this workflow when accepted DontLift product requirements, design, and architecture exist and a complete, dependency-aware implementation backlog is needed.

P6.0 establishes what slices are needed and their recommended order. P6.1 selects and plans one approved slice; P6.2 implements that separately approved plan. Backlog approval does not authorize implementation or automatically execute either later workflow.

Use the same workflow for updates: retain stable slice identities and prior decisions, inspect what changed, and obtain approval for the proposed revision.

## 4. TASK

### Phase A — Repository exploration

1. Record the branch/ref being inspected and relevant uncommitted changes. Do not switch branches, merge, or edit files to obtain a different baseline. Separate evidence from another ref from functionality available on the selected baseline.
2. Read accepted requirements, designs, architecture, ADRs, and API contracts. Identify recorded human-approved exceptions to older documents.
3. Inspect actual source, tests, dependency declarations, and available runtime evidence. Map presentation, domain, local-data, Firebase/API, authorization, and platform boundaries.
4. Classify observed functionality as completed, partial, missing, or blocked. For blocked work, also record the last known implementation stage and the exact blocker.
5. Attach evidence to each classification. A prototype, mocked test, installed package, or architecture statement alone does not prove a working production journey. Distinguish implemented-but-unverified behavior from verified completion.
6. Identify relevant accepted design/prototype references and their loading, empty, error, offline, syncing, recovery, Host/Member, and accessibility states.
7. Use `$ui-ux-pro-max` for relevant interaction/accessibility analysis and the Firebase skills above for their stated boundaries. For Cloud Functions and Admin SDK concerns, inspect the approved contracts, actual backend code, and current official Firebase documentation for the SDK/runtime in use. Do not invent a `firebase-functions` skill or treat Firestore/Auth skills as a complete backend implementation guide.

### Phase B — Feature identification

1. Inventory all major features and user journeys in the accepted requirements for the selected release. Confirm the release scope with the human if unspecified.
2. Map each journey to existing requirement identifiers and document sections. Include applicable functional and non-functional requirements; do not invent requirement IDs.
3. Identify shared capabilities and cross-feature dependencies. Check supporting journeys as well as primary flows, including history, profile, settings, hardware failures, retention, and accepted entitlement behavior where in scope.
4. Separate deferred/post-MVP and strictly excluded behavior from the implementation backlog. Record document conflicts or unclear release assignments for human resolution.

### Phase C — Slice decomposition

Break the accepted scope into small, coherent, independently demonstrable slices. Do not force a fixed count or equate a feature, screen, or requirement with exactly one slice.

Each slice should deliver one observable user journey or a bounded increment to it across the required layers. Avoid separate UI/database/API slices unless a technical prerequisite is necessary; explain why such a foundation slice cannot reasonably be included in a user journey and define its own demonstrable verification outcome.

Every slice must contain:

| Field | Required content |
|---|---|
| Slice ID | Stable, unique ID such as `SL-001`; preserve existing IDs, never renumber by priority or reuse retired IDs. |
| Feature | Parent capability and target release. |
| User journey | Actor, trigger, observable result, and demonstration scenario. |
| Scope | Included behavior and affected mobile, domain, local-data, Firebase/API, security, and platform boundaries. |
| Non-goals | Explicitly excluded behavior and the slices that own adjacent work, if known. |
| Acceptance criteria | Observable success, validation, failure, offline, retry/recovery, authorization, and relevant performance outcomes; mark non-applicable cases with a reason. |
| Dependencies | Existing slice IDs, hard prerequisites versus optional ordering preferences, and external prerequisites recorded separately. |
| Priority | Human priority where supplied; otherwise a proposed priority with rationale. Priority is distinct from dependency order. |
| Risks and external prerequisites | Contract gaps, missing decisions, provisioning, tools, devices, or third-party inputs; state their impact. |
| Current implementation status | Completed, partial, missing, or blocked, with source/test/runtime evidence and remaining verification gaps. |
| Related references | Existing requirement IDs, design sections/screens, relevant ADRs/API contracts, and actual implementation paths. |

Create a coverage matrix mapping every in-scope requirement and acceptance outcome to its owning slice(s). For split requirements, name the portion owned by each slice. Give shared capabilities one owner and let other slices depend on it. Identify gaps and overlapping ownership explicitly.

### Phase D — Dependency and priority analysis

1. Validate that all dependency IDs exist, no slice depends on itself, and the hard-dependency graph contains no cycles. Explain missing/circular dependencies and propose corrections without changing accepted requirements.
2. Recommend an implementation sequence that respects hard dependencies and human priorities. Use a table or dependency diagram when it clarifies the order; stable IDs do not encode sequence.
3. Identify necessary foundational work from repository evidence, including test/runtime readiness and contracts. Do not add generic infrastructure without a concrete dependent journey.
4. Separate work that can proceed now from work requiring a decision or external prerequisite. Show how blockers affect downstream slices and what evidence would clear them.
5. Verify local-first, Firebase ownership, sensor/lifecycle, reconciliation, entitlement, and bill invariants against applicable accepted contracts.
6. For slices involving backend commands, make the following acceptance and verification obligations explicit: Auth-derived identity; role, ownership, and lifecycle authorization inside Functions because Admin SDK bypasses Security Rules; server-side payload validation; atomic multi-document effects; receipt-backed idempotency and safe retries; safe error/log handling; and Emulator Suite integration checks for allowed, denied, concurrent, and replayed requests where relevant. Flag undefined contracts as decisions needed before P6.1/P6.2 rather than inventing endpoint schemas during decomposition.

### Phase E — Human review

Present the complete proposed backlog in chat, including the coverage matrix, dependency analysis, recommended sequence, implementation evidence, and conflicts, missing decisions, and assumptions. For revisions, also show added, changed, split, superseded, and removed slices and the impact on previously approved work.

Ask the human to approve the proposed version and its scope, non-goals, acceptance criteria, dependencies, and priorities. Explain which decisions remain unresolved. STOP for explicit approval; do not save the canonical backlog while approval is pending. Partial or conditional approval is not approval of the full backlog: resolve or clearly delimit it before saving an approved version.

### Phase F — Save approved backlog

Only after explicit approval, create or update `dontlift-mobile/docs/implementation-slices.md` with the exact approved proposal and conditions. Record approval status, date, approved scope/version, and revision history using available evidence; never fabricate an approver or approval.

Preserve previously approved decisions. Keep stable IDs and record successor IDs for splits or superseded slices. Do not silently delete or overwrite approved scope; a material change requires explicit authorization.

Make the document usable as input to P6.1: it must identify the slice, dependencies, behavior, acceptance criteria, references, readiness, and verification gaps. P6.1 must still inspect current code and obtain approval of its detailed plan. Report the saved path and stop; do not start P6.1 or P6.2.

## 5. CONSTRAINTS AND SOURCE PRECEDENCE

Use this precedence:

1. Newer explicit human-approved decisions.
2. Accepted ADRs in `docs/decisions/`.
3. `docs/software-architecture.md`.
4. `docs/api-contracts.md` for callable wire contracts.
5. `docs/product-requirements.md` for product scope and acceptance criteria.
6. `docs/product-design.md` and the accepted design decision packet for UI.
7. `docs/feature-specification.md`.
8. `docs/project-context.md` and `docs/project-brief.md` as historical context.

Human priority determines scheduling; it does not itself override accepted ADRs. Read-only prototype/design references support approved design. Current implementation/evidence establishes observed status rather than overriding target contracts; AI suggestions come after these sources.

Respect applicable repository instructions. Recorded human-approved ADR exceptions belong to the approved decisions above; apply them explicitly instead of copying obsolete prototype or specification behavior. Report unresolved conflicts with their sources and affected slices rather than silently redesigning the product or architecture.

- Planning only: never modify application/backend source, tests, dependencies, configuration, requirements, architecture, ADRs, prototypes, or prompt files during P6.0. Only the canonical backlog may be written, after approval. Do not install packages, provision resources, deploy, or run destructive checks.
- Inspect existing verification evidence; any optional read-only check must be relevant and its actual result recorded. Do not invent requirements, credentials, Firebase project IDs/resources, tests, builds, or device evidence.
- Preserve accepted Expo/React Native/TypeScript conventions. Do not introduce unrelated web-stack guidance such as HTMX, Next.js, or FastAPI.
- Treat accepted concepts and prototypes as read-only visual/interaction references. Do not copy their mock data, scripts, or static markup into production or treat simulated interactions as implemented capabilities.
- Preserve Solo offline operation, SQLite-first persistence, durable outbox, and duplicate-safe synchronization through `syncEvents`. Firestore cache does not replace the SQLite outbox.
- Firebase native SDK owns token persistence. Keep server-owned lifecycle, scores, quotas, entitlement, and bill outcomes behind approved command boundaries; use membership documents for room authorization.
- Skill defaults do not override accepted choices: Firebase Auth uses Email/Password for MVP, Firestore uses Standard edition, and native integration uses React Native Firebase in a Development Build. Do not switch to social login, Enterprise edition, another SDK/backend, or provisioning/deployment merely because a supporting skill suggests it.
- Apply ADR-008 to background transitions and the 3-Second Grace Period; preserve the Local Premium/Server Premium distinction in ADR-007.
- Preserve integer VND arithmetic, non-negative shares, exact share totals, and non-custodial VietQR settlement. No automatic bank verification.
- Plan the relevant verification obligations: physical Android/iOS device evidence for sensor/lifecycle behavior, restart/reconnect/retry/duplicate delivery for offline sync, Emulator Suite checks for Firebase, and arithmetic properties for bill allocation. Mock tests do not prove native persistence.
- Do not execute P6.1/P6.2 automatically, approve your own backlog, or overwrite approved decisions without explicit authorization. Skill defaults must remain within this workflow's planning-only scope and output/approval limits.

## 6. EXPECTED OUTPUT

Before approval, return one complete, reviewable proposal in chat containing:

1. Baseline, target release, inspected inputs, and implementation/verification inventory.
2. Feature and journey inventory with requirement/design traceability.
3. The full backlog with every required slice field.
4. Requirement/acceptance coverage matrix, exclusions/deferred scope, gaps, and overlap checks.
5. Validated dependencies, recommended sequence, and readiness/blockers.
6. Risks, missing decisions, assumptions, and the explicit approval request.
7. A concise change summary against the existing backlog when updating it.

After approval, save that approved backlog to the canonical output and report its path, revision, conditions, and remaining blockers. The backlog is planning evidence; it does not establish that code has been implemented or verified.

## 7. SAVE / UPDATE + HUMAN REVIEW + VALIDATION

Before requesting approval, verify:

- Every in-scope requirement and acceptance outcome is covered; deferred/excluded behavior is separated, and unresolved coverage is visible.
- Each slice has all required fields, a bounded demonstration, explicit non-goals, and justified foundations where necessary.
- IDs are unique and stable, all dependency references resolve, and the hard-dependency graph is acyclic.
- The recommended order respects prerequisites; external blockers and optional ordering preferences are distinguished.
- Source references exist on the recorded baseline, or their external provenance/missing status is explicit.
- Actual implementation evidence is separated from design intent, simulation, and unverified behavior.
- Relevant offline/recovery, security, platform, sensor, sync, entitlement, and bill constraints are reflected in acceptance criteria.
- Conflicts, changed approved decisions, and assumptions are presented for human resolution.
- The proposal is directly usable by P6.1 without replacing P6.1's detailed-plan approval gate.

While approval is pending, keep the draft in chat and leave the canonical file unchanged. After explicit approval, write only `dontlift-mobile/docs/implementation-slices.md`, preserve prior approved decisions and history, and verify that its content matches the approved proposal. Stop for human review of the saved artifact; do not implement features or begin later workflows.
